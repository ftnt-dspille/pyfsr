pyfsr.api.multitenancy¶

Dedicated-tenant multitenancy: run a remote FortiSOAR node as a tenant of this master.

A dedicated tenant is a remote FortiSOAR node that this master manages. Setting one up is a two-sided dance that the product’s UI performs with a handful of calls; this module wraps them so the same steps can be scripted. Accessed as client.multitenancy.

Master side (the box that owns the tenant):

  1. MultitenancyAPI.add_dedicated_tenant() creates the tenant record and its master-side agent record (isDedicated tenant + agentId = the tenant node’s 32-hex tenantId).

  2. MultitenancyAPI.wait_for_health() polls the agent until the remote node connects (Remote Node Connected).

  3. MultitenancyAPI.export_config() returns the bundle the tenant needs (address, ports, router and agent credentials, agentId = this master’s id).

  4. MultitenancyAPI.encryption_key() returns the key the tenant must be configured with; it is the agent record’s encryptionKey and changes whenever that record is re-created.

  5. MultitenancyAPI.delete_tenant() removes the tenant (and its agent record with it).

Tenant side (the remote node being attached):

  1. MultitenancyAPI.configure_master() creates the Master router and the Master agent from the exported config and the key from step 4.

  2. MultitenancyAPI.status() shows the Master agent’s configstatus (Connection Verified once the link works).

Idempotency. The product’s UI is not idempotent: when the tenant-side agent create fails after the router was created, a retry collides with the leftover router. Router and agent uuids here are derived from the master’s agentId, so a leftover is found by uuid and reported as a MultitenancyError with leftover_router set. Pass replace_leftover=True to delete the leftover and configure again.

Secrets. MultitenancyAPI.export_config() returns an ExportedConfig whose repr/str mask the password, certificate and key fields. Returned agent/tenant records have the secret fields removed. Nothing here logs secret values.

Example

>>> client = demo_client()
>>> tenant, agent = client.multitenancy.add_dedicated_tenant("branch-7")
>>> client.multitenancy.wait_for_health("branch-7", "Remote Node Connected", timeout=600)
'Remote Node Connected'
>>> config = client.multitenancy.export_config("branch-7")
>>> key = client.multitenancy.encryption_key("branch-7")
>>> # on the tenant box (its own client):
>>> tenant_client.multitenancy.configure_master(config, key)
>>> client.multitenancy.delete_tenant("branch-7")

add_dedicated_tenant(name: str, tenant_id: str, *, sme: str | collections.abc.Mapping[str, Any] | None = None, owners: collections.abc.Sequence[Any] | None = None, version: str | None = None) → tuple[pyfsr.models._multitenancy.Tenant, pyfsr.models._agents.Agent][source]¶

Create a dedicated tenant and its master-side agent record; return (tenant, agent).

Two calls, as the UI makes them: POST /api/3/tenants (isDedicated, the tenantId, owners) and POST /api/3/agents (agentId = the same tenantId, version, agentType = "FSR Node", authType = "Basic Auth", the router, and the tenant IRI). Picklist values are resolved by name, not hard-coded uuids.

tenant_id is the 32-hex tenantId of the tenant node’s own Self tenant. It is required: the master cannot know it (read it on the tenant node). sme is the SME router (record, IRI or uuid); default is first(). owners are team names/IRIs (default "SOC Team", the team the message router can read). version defaults to the master’s build version without its build number.

A failure on the agent call leaves the tenant behind; delete_tenant() removes it.

Example

>>> client = demo_client()
>>> tenant, agent = client.multitenancy.add_dedicated_tenant("branch-7")
>>> tenant.name
'branch-7'

configure_master(config: collections.abc.Mapping[str, Any], encryption_key: str, *, owners: collections.abc.Sequence[Any] | None = None, role: str | None = None, tenants: collections.abc.Sequence[Any] | None = None, replace_leftover: bool = False) → pyfsr.models._agents.Agent[source]¶

Attach this node to its master: create the Master router, then the Master agent.

Run on the tenant box. config is the master’s export_config() result (a plain mapping works too); encryption_key is encryption_key() from the master.

  1. POST /api/3/routers with the router uuid (derived from config["agentId"]), apiPort 15671, the address/sni/ports/credentials from config, the key, and configstatus.

  2. POST /api/3/agents?$relationships=true&$asJson=true for the Master agent, with the same key, the router IRI, owners (default "SOC Team"), authType from config, and agentType "FSR Node". role and tenants are sent only when given.

Before anything is written, a leftover from an earlier attempt (router or agent with the derived uuid) raises MultitenancyError with leftover_router set. Pass replace_leftover=True to delete it first. A decrypt failure (DB Password decrypt failed, the key does not match the master) or a uuid conflict on the agent step also raises MultitenancyError, and the router is left behind for replace_leftover=True on the retry.

Example

>>> tenant = demo_client()  # the tenant box's client
>>> config = {"agentId": "0123456789abcdef0123456789abcdef", "address": "master.example.com",
...           "tcpPort": 443, "sni": "master.example.com", "routerUsername": "router",
...           "password": "<redacted>", "certificate": "<pem>", "username": "agent",
...           "vhost": "/", "authType": "Basic Auth"}
>>> tenant.multitenancy.configure_master(config, "<encryption-key>")

Detach this node from its master: delete its Master agent, router and tenant; return their uuids.

Run on the tenant box, after delete_tenant() on the master. Finds the records by name through the query API (the list endpoint hides them, and a UI-made record has a random uuid), deleting agents before routers. Returns [] when the node has none.

push_playbooks(collections: collections.abc.Sequence[str], tenants: collections.abc.Sequence[str], *, replace: bool = True) → dict[str, Any][source]¶

Push playbook collections from this master to dedicated tenants.

The same call the UI’s Tenant Manager > Push Playbooks makes. Each tenant gets a copy with the same collection and playbook uuids. Every playbook pushed with remoteExecutableFlag set also gets a playbook alias, named after the playbook and mapped to each tenant (see playbook_alias()).

Parameters:

  • collections – Collection uuids or exact names on this master.

  • tenants – Tenant names (resolved with tenant_id()) or 32-hex tenant ids.

  • replace – Replace a collection of the same name on the tenant (the UI default).

Example

>>> client = demo_client()
>>> client.multitenancy.push_playbooks(["MT Health - Tenant"], ["branch-7"])
